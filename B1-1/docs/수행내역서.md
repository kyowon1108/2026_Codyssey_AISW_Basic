## 1. 실습 환경

Ubuntu 22.04 컨테이너에서 작업했다. 컨테이너 옵션 두 개는 이 과제에 필수다.

| 옵션 | 이유 |
|---|---|
| `--privileged` | UFW가 netfilter/iptables를 조작하려면 NET_ADMIN 권한이 필요하다 |
| `--init` | PID 1이 종료된 자식 프로세스를 회수하게 한다. 없으면 앱이 죽어도 좀비가 남아 헬스체크가 오탐한다 (6.3) |

포트는 `-p 20022:20022 -p 15034:15034`로 호스트에 매핑했다. 호스트에서 SSH 접속과 앱 포트 도달을 직접 확인하기 위해서다.

```bash
./env/run.sh                                            # 이미지 빌드 + 컨테이너 기동
docker exec agent-lab bash /mnt/B1-1/setup/run_all.sh   # 01~08 일괄 수행
```

## 2. 기본 보안 및 네트워크

### 2.1 SSH (`setup/01_ssh.sh`)

| 항목 | 설정값 |
|---|---|
| 접속 포트 | 22 → **20022** |
| Root 원격 로그인 | **`PermitRootLogin no`** |

`/etc/ssh/sshd_config`를 직접 수정하되, `sshd -t`로 문법을 검증한 뒤에만 재시작한다.
설정이 깨진 상태로 sshd를 재시작하면 원격 접속 수단을 통째로 잃기 때문이다. 원본은 `/etc/ssh/sshd_config.orig`로 백업한다.

![컷 2. sshd_config 설정값과 20022 리슨 상태](evidence/img/02_ssh_config.png)

설정 파일만으로는 실제로 막히는지 알 수 없어서 로그인을 직접 시도했다.

| 시나리오 | 결과 |
|---|---|
| `agent-admin` → 20022 포트 | 성공 (`로그인 성공: agent-admin@agent-lab`) |
| `agent-admin` → 22 포트 | 실패 (`Connection refused`) |
| `root` → 20022 포트, 올바른 비밀번호 | 거부 (`Permission denied`) |

![컷 3. 일반 계정 접속 성공, 22번 거부, root 거부](evidence/img/03_ssh_login.png)

root 테스트는 비밀번호가 틀려서 막힌 경우와 구분하려고 root 비밀번호를 일부러 정확히 설정한 뒤 시도했다.
그래도 거부되면 `PermitRootLogin no`가 동작하는 것이다. 테스트 후 root 계정은 `passwd -l`로 다시 잠갔다.

**포트 변경과 root 차단이 기본 보안인 이유**

22번은 인터넷 전역 스캐너가 가장 먼저 두드리는 포트다. 포트만 옮겨도 자동화된 무차별 대입 시도량이 크게 준다.
root는 어느 서버에나 반드시 존재하는 계정이라, root 원격 로그인을 열어두면 공격자는 계정명을 추측하는 단계를 건너뛰고 비밀번호만 뚫으면 된다.
root를 막으면 유효한 계정명과 비밀번호를 모두 맞춰야 하고, 관리 작업이 일반 계정 로그인 뒤 `sudo`로 이루어지므로 누가 무엇을 했는지 감사 로그에 남는다.
다만 포트 변경은 스캔 노이즈를 줄일 뿐 인증을 강화하지는 않는다. 실제 운영이라면 키 기반 인증과 `PasswordAuthentication no`를 함께 적용해야 한다.

### 2.2 방화벽 (`setup/02_firewall.sh`)

UFW를 선택했다. 기본 정책(deny) → 허용 규칙 → 활성화 순서를 지켰다.
`ufw enable`을 먼저 하면 그 순간 20022 규칙이 없어 원격 세션이 끊긴다.

![컷 4. UFW 활성화 상태와 허용 규칙 2개](evidence/img/04_firewall.png)

허용된 인바운드는 `15034/tcp`, `20022/tcp` 두 개뿐이고 22/tcp 규칙은 없다.

`monitor.sh`가 방화벽 상태를 조회할 수 있도록 조회 전용 sudo 규칙만 부여했다 (6.2).

```
# /etc/sudoers.d/agent-monitor
%agent-core ALL=(root) NOPASSWD: /usr/sbin/ufw status
```

**필요한 포트만 여는 이유**

열려 있는 포트는 그대로 공격 표면이 된다.
기본 정책을 deny로 두면 나중에 실수로 뜬 서비스(개발용 디버그 포트, 임시 DB 등)가 외부에 노출되는 일까지 함께 막힌다.

## 3. 계정, 그룹, 권한 체계 (`setup/03_users_groups.sh`, `setup/04_dirs_acl.sh`)

### 3.1 계정과 그룹

| 계정 | 역할 | 소속 그룹 |
|---|---|---|
| `agent-admin` | 운영/관리, cron 실행자 | `agent-common`, `agent-core` |
| `agent-dev` | 개발/운영, monitor.sh 작성자 | `agent-common`, `agent-core` |
| `agent-test` | QA/테스트 | `agent-common` |

![컷 5. 계정 3개와 그룹 멤버십](evidence/img/05_users.png)

`agent-test`가 `agent-core`에 포함되지 않는 것이 이 설계의 핵심이라, 스크립트에서 이 조건을 따로 검사한다.

### 3.2 디렉토리 구조와 권한

| 경로 | 소유자:그룹 | 모드 | 의도 |
|---|---|---|---|
| `/home/agent-admin` | `agent-admin` | 755 | agent-dev가 하위 경로까지 통과할 수 있어야 함 |
| `$AGENT_HOME` | `agent-admin:agent-common` | 750 | 세 계정 모두 하위로 진입만 가능 |
| `$AGENT_HOME/upload_files` | `agent-admin:agent-common` | 2770 | 공유 영역, common R/W |
| `$AGENT_HOME/api_keys` | `agent-admin:agent-core` | 2770 | 보안 영역, core ONLY |
| `$AGENT_HOME/bin` | `agent-dev:agent-core` | 750 | 스크립트 작성자 소유 |
| `/var/log/agent-app` | `agent-admin:agent-core` | 2770 | 보안 영역, core ONLY |

권한 설계에서 걸리기 쉬운 두 지점이 있다.

**`$AGENT_HOME`의 그룹은 `agent-core`가 아니라 `agent-common`이다.**
`agent-core`로 두면 `agent-test`가 상위 디렉토리를 통과하지 못해, 정작 공유 디렉토리인 `upload_files`에 들어갈 수 없다.
리눅스에서 파일 접근은 경로상의 모든 디렉토리에 실행(x) 권한이 있어야 가능하다.

**`/home/agent-admin`은 755여야 한다.**
`monitor.sh`가 `agent-admin`의 홈 아래에 있는데, 작성자인 `agent-dev`가 홈을 통과하지 못하면 자기가 만든 스크립트에 접근할 수 없다.

`2770`의 setgid 비트는 이 디렉토리에서 새로 생기는 파일이 부모 디렉토리의 그룹을 상속하게 한다.
개인 그룹(`agent-dev` 등)으로 파일이 생겨서 다른 팀원이 못 읽는 상황을 구조적으로 막는다.

### 3.3 ACL

기본 권한 비트로는 그룹을 하나밖에 지정할 수 없어 ACL로 의도를 명시했다.
`default:` ACL을 함께 걸어 이후 생성되는 파일에도 같은 정책이 적용된다.

![컷 6. 디렉토리 권한과 api_keys 의 ACL](evidence/img/06_dirs_acl.png)

### 3.4 접근 테스트

계정을 바꿔가며 직접 시도한 결과다.

| 계정 | 대상 | 기대 | 결과 |
|---|---|---|---|
| `agent-test` | `upload_files` 파일 생성 | 허용 | allow |
| `agent-dev` | `upload_files` 파일 생성 | 허용 | allow |
| `agent-test` | `api_keys` 접근 | 차단 | deny |
| `agent-dev` | `api_keys` 접근 | 허용 | allow |
| `agent-test` | `/var/log/agent-app` 접근 | 차단 | deny |
| `agent-admin` | `/var/log/agent-app` 쓰기 | 허용 | allow |
| `agent-test` | `monitor.sh` 실행 | 차단 | deny |

![컷 7. 계정별 접근 테스트 결과](evidence/img/07_access_test.png)

**공유 영역과 보안 영역을 나누는 이유**

협업에는 모두가 읽고 쓸 공간이 필요하지만 API 키와 운영 로그는 성격이 다르다.
키가 유출되면 외부 시스템 권한이 통째로 넘어가고, 로그가 조작되면 장애 원인 추적과 사후 감사가 불가능해진다.
그래서 협업 편의가 필요한 `upload_files`와 최소 권한이 필요한 `api_keys`, 로그 디렉토리를 그룹 단위로 분리했다.
QA 담당인 `agent-test`는 업무상 키와 운영 로그가 필요 없으므로 `agent-core`에서 제외된다.

## 4. 애플리케이션 실행 환경 (`setup/05_app_env.sh`, `setup/06_run_app.sh`)

### 4.1 환경 변수

| 변수 | 값 |
|---|---|
| `AGENT_HOME` | `/home/agent-admin/agent-app` |
| `AGENT_PORT` | `15034` |
| `AGENT_UPLOAD_DIR` | `$AGENT_HOME/upload_files` |
| `AGENT_KEY_PATH` | `$AGENT_HOME/api_keys` (4.2 참고) |
| `AGENT_LOG_DIR` | `/var/log/agent-app` |

환경 변수는 두 곳에 정의했다.

| 파일 | 읽는 주체 |
|---|---|
| `/etc/profile.d/agent-env.sh` | 로그인 셸 (사람이 SSH로 접속했을 때) |
| `$AGENT_HOME/agent.env` | `monitor.sh`가 명시적으로 `source` (cron용) |

cron은 로그인 셸이 아니라서 `/etc/profile.d`를 읽지 않는다. 이 과제에서 가장 흔한 실패 지점이다.
셸에서 수동 실행할 땐 잘 되는 스크립트가 cron에서만 조용히 실패한다.
`monitor.sh`는 환경 파일을 직접 읽고, 그마저 없으면 기본값으로 동작하도록 이중으로 막아뒀다.

**환경 변수로 실행 환경을 고정하는 이유**

경로를 스크립트마다 하드코딩하면 앱과 모니터링, 배포 스크립트가 서로 다른 경로를 보게 되는 순간을 아무도 눈치채지 못한다.
한곳에 모아두면 변경 지점이 하나가 되고, 앱 부팅 시퀀스가 그 값을 검증하기 때문에 잘못된 설정이 서비스 시작 시점에 드러난다.
확인은 `runuser -l agent-admin -c 'env | grep ^AGENT_'`로 실제 실행 계정의 셸에서 했다. root 셸에서 확인하면 의미가 없다.

### 4.2 과제 명세와 제공 앱의 차이

제공된 바이너리를 실행해 보니 과제 문서와 앱의 요구가 두 곳 달랐다.

| 항목 | 과제 문서 | 제공 앱의 실제 요구 |
|---|---|---|
| `AGENT_KEY_PATH` | `$AGENT_HOME/api_keys/t_secret.key` (파일 경로) | `$AGENT_HOME/api_keys` (디렉토리 경로) |
| 키 파일명 | `t_secret.key` | `secret.key` |

```
[2/5] Verifying Environment Variables     [FAIL]
   >>> Key Path Mismatch. Expected: /home/agent-admin/agent-app/api_keys

[3/5] Checking Required Files             [FAIL]
   >>> Missing File: secret.key
   >>>    (Expected location: /home/agent-admin/agent-app/api_keys/secret.key)
```

실제 키 파일은 과제 명세대로 `t_secret.key`로 만들고, 앱이 찾는 `secret.key`는 같은 디렉토리 안의 심볼릭 링크로 연결했다.
키를 두 벌 복사하면 관리 지점이 갈라져 한쪽만 교체되는 사고가 난다.

```
$ ls -l $AGENT_HOME/api_keys
lrwxrwxrwx 1 agent-admin agent-core 12 secret.key -> t_secret.key
-rw-r-----+ 1 agent-admin agent-core 19 t_secret.key      # 내용: agent_api_key_test
```

## 5. 관제 자동화 스크립트 (`scripts/monitor.sh`)

| 항목 | 값 |
|---|---|
| 배치 경로 | `$AGENT_HOME/bin/monitor.sh` |

```
[2026-08-22 18:09:02] PID:3081 CPU:1.9% MEM:34.0% DISK_USED:4%
```

### 5.2 종료 코드

| 코드 | 상황 |
|---|---|
| 0 | 정상 (임계값 경고 포함) |
| 1 | Health Check 실패 (프로세스 부재 / 포트 미개방) |
| 2 | 실행 환경 오류 (로그 디렉토리 부재 또는 쓰기 불가) |

방화벽 비활성과 임계값 초과는 경고만 하고 종료하지 않는다. 여기서 멈추면 정작 필요한 자원 수치가 기록되지 않는다.

### 5.3 자원 수집 방식

| 지표 | 방식 |
|---|---|
| CPU | `/proc/stat`을 1초 간격으로 두 번 읽어 차이로 계산 |
| MEM | `/proc/meminfo`의 `(MemTotal - MemAvailable) / MemTotal` |
| DISK | `df -P /`의 Used% |

`top -bn1`의 첫 샘플은 부팅 이후 누적 평균이라 현재 부하를 반영하지 못해서 쓰지 않았다.
메모리도 `free`의 used 대신 `MemAvailable`을 기준으로 삼았다. buff/cache는 필요하면 회수되는 메모리라 used에 넣으면 사용률이 과대 계상된다.

### 5.4 로그 기록과 용량 관리

```
[2026-08-22 18:09:02] PID:3081 CPU:1.9% MEM:34.0% DISK_USED:4%
[2026-08-22 18:10:02] PID:3081 CPU:1.7% MEM:36.2% DISK_USED:4%
```

`monitor.log`가 10MB를 넘으면 `.1`, `.2` 순으로 밀어내고 가장 오래된 파일을 버려 최대 10개를 유지한다.
logrotate 대신 스크립트 내부 로직으로 구현한 이유는 logrotate 설정이 root 소유 영역인데 이 스크립트는 일반 계정으로 돌기 때문이다.
스크립트가 자기 로그를 직접 관리하면 추가 권한이 필요 없다.

### 5.5 예외 동작 검증

| 검증 | 조건 | 결과 |
|---|---|---|
| 로그 로테이션 | `monitor.log` 11MB | `Log rotated (11534336 bytes >= 10485760 bytes)`, `monitor.log.1` 생성, exit 0 |
| 방화벽 비활성 | `ufw disable` | `[WARNING] Firewall is INACTIVE.` 출력 후 자원 수집 계속, exit 0 |
| 앱 중지 | 프로세스 종료 | `Checking process ... [FAIL]`, exit 1 |
| 좀비 프로세스 | `<defunct>` 상태 | 오탐 없이 exit 1 (6.3) |
| CPU 임계값 | 인위적 부하 | `[WARNING] CPU threshold exceeded (99.9% > 20%)` |
| MEM 임계값 | 평상시 | `[WARNING] MEM threshold exceeded (34.3% > 10%)` |
| DISK 임계값 | 임계값을 1%로 조정 | `[WARNING] DISK threshold exceeded (4% > 1%)` |

![컷 12. CPU 부하 상황에서 임계값 경고](evidence/img/12_threshold_cpu.png)

![컷 13. 앱 중지 시 Health Check 실패와 exit 1](evidence/img/13_health_fail.png)

DISK는 루트 파티션 사용률이 4%라 80% 임계값을 넘기려면 디스크를 실제로 채워야 해서 위험하다.
대신 임계값을 환경 변수로 덮어쓸 수 있게 만들어 같은 비교 분기가 동작하는지 확인했다. 기본값은 명세대로 80%다.

## 6. 검증 중 발견해 고친 문제

동작을 확인하는 과정에서 결함 네 개가 나왔다. 모두 수동 실행은 성공하는데 실제 장애 상황에서만 틀리는 유형이다.

### 6.1 cron의 PATH

cron의 기본 PATH는 `/usr/bin:/bin`뿐이라 `/usr/sbin/ufw`를 찾지 못한다.
`monitor.sh` 상단에서 PATH를 명시적으로 설정해 해결했다.

### 6.2 `ufw status`의 root 권한 요구

`monitor.sh`는 일반 계정으로 도는데 `ufw status`는 root를 요구한다.
sudo 전체 권한을 주는 대신 조회 명령 하나만 NOPASSWD로 허용했고(`%agent-core ... /usr/sbin/ufw status`), 그마저 불가능한 환경을 위해 `/etc/ufw/ufw.conf`를 읽는 폴백을 뒀다.
방화벽을 변경할 권한은 주지 않는다.

### 6.3 `pgrep -f`의 오탐

헬스체크를 `pgrep -f agent-app-linux`로만 짰더니 앱이 죽었는데도 `[OK]`를 반환하는 경우가 두 가지 나왔다.

**좀비 프로세스**

앱이 죽은 뒤 부모가 회수하지 않으면 `<defunct>` 상태로 프로세스 테이블에 남고, `pgrep`은 이를 그대로 반환한다.

```
$ ps -eo pid,stat,args | grep agent-app-linux
 3000 Z    [agent-app-linux] <defunct>
$ pgrep -af agent-app-linux
3000 agent-app-linux
```

**명령줄에 패턴 문자열을 가진 무관한 프로세스**

`pgrep -f`는 명령줄 전체를 훑기 때문에 패턴을 인자로 가진 셸, 에디터, grep까지 잡는다.
검증 중 `monitor.sh`가 자기를 실행한 셸을 앱으로 착각해 `Checking process 'bash'... [OK] (PID: 1965)`를 출력했다.

후보 PID를 두 번 거르도록 고쳤다. 실행 파일 이름(`ps -o comm=`)이 앱 이름과 일치할 것, 프로세스 상태가 `Z`가 아닐 것.
컨테이너에는 `--init`을 줘 PID 1이 좀비를 회수하도록 환경도 함께 바꿨다.

### 6.4 앱 종료 시 자식 프로세스 잔존

`06_run_app.sh stop`이 부모 PID에만 SIGINT를 보내 앱이 종료되지 않았다.
앱은 워커 자식 프로세스를 함께 띄우고, 터미널에 연결되지 않은 상태에서는 SIGINT에 반응하지 않았다.
프로세스 그룹 전체에 시그널을 보내고 `INT → TERM → KILL`로 단계적으로 강화하도록 고쳤다. 실제로는 SIGTERM에서 종료된다.

## 7. 자동 실행 (`setup/08_cron.sh`)

`agent-admin` 계정의 crontab에 매분 실행으로 등록했다.

```
$ crontab -u agent-admin -l
# Agent App 시스템 관제 - 매분 실행
MAILTO=""
* * * * * /home/agent-admin/agent-app/bin/monitor.sh >/dev/null 2>>/var/log/agent-app/monitor.cron.log
```

표준출력은 버리고 표준에러만 별도 파일로 보낸다.
`monitor.log`에는 규정된 포맷의 한 줄만 남아야 해서 콘솔 출력과 섞지 않되, 실패 메시지는 추적할 수 있게 남겼다.

등록 후 시간이 흐르는 동안 누적 상태를 관측했다.

```
### t=0 (18:02:03)  라인 수: 2
### t=150초 (18:04:33)  라인 수: 4
[2026-08-22 18:02:02] PID:465 CPU:1.2% MEM:35.3% DISK_USED:4%
[2026-08-22 18:03:02] PID:465 CPU:0.8% MEM:34.4% DISK_USED:4%
[2026-08-22 18:04:02] PID:465 CPU:1.8% MEM:36.1% DISK_USED:4%
--- cron 에러 로그 --- (size: 0 bytes)
```

![컷 11. crontab 등록과 monitor.log 자동 누적](evidence/img/11_cron.png)

매분 한 줄씩 누적되고 cron 에러 로그는 비어 있다.

**주기 실행과 로그 보존 정책이 필요한 이유**

장애는 사람이 보고 있지 않을 때 일어난다. 주기 수집이 없으면 장애 시점의 CPU와 메모리 값을 되짚을 방법이 없어 원인 분석이 추측이 된다.
반대로 로그를 무한정 쌓으면 로그가 디스크를 채워 새로운 장애를 만든다. 관제 로그가 서버를 죽이는 건 흔한 사고다.
남기되 상한을 두고 오래된 것부터 버리는 정책이 함께 가야 한다.

## 부록: 주요 명령어

```bash
# SSH
sed -i -E 's|^[[:space:]]*#?[[:space:]]*Port[[:space:]]+.*|Port 20022|' /etc/ssh/sshd_config
sshd -t && service ssh restart
ss -tulnp | grep -i sshd

# 방화벽
ufw default deny incoming && ufw default allow outgoing
ufw allow 20022/tcp comment 'SSH (changed port)'
ufw allow 15034/tcp comment 'Agent APP'
ufw --force enable && ufw status verbose

# 계정 / 그룹
groupadd agent-common && groupadd agent-core
useradd -m -s /bin/bash agent-admin
usermod -aG agent-common,agent-core agent-admin
id agent-admin

# 디렉토리 / 권한 / ACL
chown agent-admin:agent-core /home/agent-admin/agent-app/api_keys
chmod 2770 /home/agent-admin/agent-app/api_keys
setfacl -m g:agent-core:rwx -m o::--- /home/agent-admin/agent-app/api_keys
setfacl -d -m g:agent-core:rwx -d -m o::--- /home/agent-admin/agent-app/api_keys
getfacl -p /home/agent-admin/agent-app/api_keys

# 앱 / 스크립트 배치
printf 'agent_api_key_test\n' > $AGENT_HOME/api_keys/t_secret.key
install -o agent-dev -g agent-core -m 750 monitor.sh $AGENT_HOME/bin/monitor.sh

# cron
service cron start
crontab -u agent-admin -l
```
